# Глава 3. Метод

В настоящей главе подробно описывается архитектура разработанной
аудио-визуальной системы распознавания речи и методика её обучения.
Раздел 3.1 содержит общую схему системы. Разделы 3.2 и 3.3 описывают
модули предобработки аудио и видео соответственно. Разделы 3.4–3.6
рассматривают аудио-энкодер, видео-энкодер и модуль слияния
модальностей. Раздел 3.7 посвящён выходной CTC-голове. Раздел 3.8
описывает стратегию обучения, включающую аугментации и modality
dropout. Наконец, раздел 3.9 описывает пайплайн инференса в режиме,
близком к реальному времени.

## 3.1. Общая схема системы

Предложенная архитектура представляет собой end-to-end нейронную сеть,
принимающую на вход одновременно аудио-сигнал и видеоряд лица
говорящего и выдающую транскрипцию произнесённого текста. Общая схема
показана на рис. 3.1.

```
┌──────────────────────────────────────────────────────────────────┐
│                      AVSR-МОДЕЛЬ                                  │
│                                                                   │
│   аудио (wav, 16 кГц)    →  Мел-спектрограмма    (B, 80, T_a)    │
│                                       │                           │
│                                       ▼                           │
│                          ┌──────────────────────┐                 │
│                          │   AudioEncoder       │                 │
│                          │   (Whisper-small,    │                 │
│                          │      замороженный)   │                 │
│                          └──────────┬───────────┘                 │
│                                     ▼  (B, T_a', 768)             │
│                                     │                             │
│   видео (кадры 25 FPS)   →  Кропы губ (96×96)    (B, T_v, 1, 96, 96)
│                                     │                             │
│                                     ▼                             │
│                          ┌──────────────────────┐                 │
│                          │   VideoEncoder       │                 │
│                          │   3D-Conv → ResNet18 │                 │
│                          │   → Transformer×4    │                 │
│                          └──────────┬───────────┘                 │
│                                     ▼  (B, T_v, 512)              │
│                                     │                             │
│                          ┌──────────┴───────────┐                 │
│                          │  CrossAttentionFusion│                 │
│                          │  (a↔v, 2 слоя)       │                 │
│                          └──────────┬───────────┘                 │
│                                     ▼  (B, T_a', 512)             │
│                          ┌──────────────────────┐                 │
│                          │  CTC head            │                 │
│                          │  Linear(512, 29)     │                 │
│                          └──────────┬───────────┘                 │
│                                     ▼  (B, T_a', 29)              │
│                          ┌──────────────────────┐                 │
│                          │  CTC greedy decode   │                 │
│                          └──────────┬───────────┘                 │
│                                     ▼                             │
│                              «hello world»                        │
└──────────────────────────────────────────────────────────────────┘
```
**Рис. 3.1.** Архитектура AVSR-системы.

Модель реализована на языке Python с использованием фреймворка PyTorch
(версия 2.x). Все компоненты — модули предобработки, энкодеры, модуль
слияния, CTC-голова — реализованы как наследники `torch.nn.Module` и
поддерживают как обучение, так и инференс. Конфигурация всех
гиперпараметров вынесена в YAML-файл, который загружается через
библиотеку OmegaConf.

## 3.2. Предобработка аудио

Сырой аудио-сигнал представляет собой последовательность отсчётов
амплитуды звуковой волны. Для современных моделей распознавания речи в
качестве входа используется не сама волна, а её спектральное
представление в виде **лог-мел-спектрограммы**.

Алгоритм построения лог-мел-спектрограммы:

1. **Ресэмплинг** аудио к стандартной для речи частоте 16 кГц
   (`torchaudio.functional.resample`).
2. **Нормализация** амплитуды: деление на пиковое значение для устранения
   зависимости от уровня записи.
3. **STFT** (Short-Time Fourier Transform) с параметрами:
   - размер FFT: 512;
   - длина окна: 400 отсчётов (25 мс);
   - шаг окна: 160 отсчётов (10 мс).
   Перекрытие соседних окон позволяет получить более гладкое временное
   представление; шаг 10 мс соответствует 100 мел-фреймам в секунду.
4. **Мел-фильтрбанк**: 80 треугольных фильтров на мел-шкале, имитирующей
   логарифмическое восприятие частот человеческим ухом.
5. **Логарифмирование** значений с добавлением малой константы для
   численной стабильности: `log(mel + 1e-9)`.

На выходе для аудио длительностью t секунд получаем тензор
размерности `(80, T_a)`, где `T_a ≈ 100·t`. Параметры выбраны в полном
соответствии с моделью Whisper, что позволяет напрямую подавать наш
выход на её вход.

## 3.3. Предобработка видео

Задача предобработки видео — выделить из каждого кадра область
**губ говорящего** в виде квадратного кропа фиксированного размера. Для
этого используется библиотека **MediaPipe FaceLandmarker** (Tasks API)
от Google, реализующая каскадный детектор лица BlazeFace и регрессор
478 ключевых точек лица.

Алгоритм извлечения ROI губ:

1. Кадр в формате BGR конвертируется в RGB.
2. Передаётся в `FaceLandmarker` в режиме `RunningMode.VIDEO`, что
   использует трекинг между кадрами и снижает вычислительные затраты.
3. Из 478 ландмарок выбираются ~40 индексов, соответствующих внешнему и
   внутреннему контурам губ.
4. Вычисляется bounding box, охватывающий все губные точки.
5. Bounding box преобразуется к квадратной форме (по большей стороне) и
   расширяется на 20% во все стороны для захвата окружающей области.
6. Соответствующий участок кадра вырезается, конвертируется в градации
   серого и масштабируется до фиксированного размера 96×96 пикселей
   с интерполяцией CUBIC.

На выходе для видео из `T_v` кадров получаем тензор размерности
`(T_v, 1, 96, 96)` с типом float32 и значениями в диапазоне [0, 1].
Кадры, на которых лицо не было обнаружено, пропускаются с
протоколированием доли пропусков.

С учётом того, что MediaPipe выполняется на CPU и обработка одного
кадра занимает порядка 20–30 мс, предобработку всего датасета
производят однократно с сохранением результата в кешированные `.npy`
файлы. Повторный прогон MediaPipe внутри `__getitem__` тренировочного
датасета был бы недопустимо медленным.

## 3.4. Аудио-энкодер

В качестве аудио-энкодера используется **encoder часть модели
Whisper-small** от OpenAI, загружаемой через библиотеку HuggingFace
`transformers`. Декодер Whisper в работе не используется, так как
выходная голова системы — CTC, не требующая авторегрессивной генерации.

Размерности:
- вход энкодера: мел-спектрограмма `(B, 80, 3000)` — Whisper требует
  ровно 30 секунд аудио; более короткие входы паддятся нулями;
- внутренний `d_model = 768`;
- два Conv1d слоя со stride 2 в начале энкодера уменьшают временное
  разрешение в 4 раза (с 3000 до 1500 фреймов);
- выход энкодера: `(B, 1500, 768)`.

Так как реальная длина аудио в работе ограничена 15 секундами, реальная
длина выхода составляет `ceil(T_a / 2)` фреймов; остальная часть из 1500
фреймов является паддингом, который игнорируется на последующих стадиях
через механизм масок внимания.

**Веса энкодера заморожены** (`requires_grad = False` для всех
параметров). Такое решение оправдано следующими соображениями:

1. Whisper-small предобучен на 680 000 часах речи — на несколько порядков
   больше, чем доступно в условиях курсовой работы. Дообучение на
   маленьком датасете рискует ухудшить, а не улучшить качество.
2. Замораживание Whisper уменьшает количество обучаемых параметров с
   ~280 миллионов до ~30 миллионов, что критически важно для
   тренировки на бесплатной GPU.
3. Замораживание исключает необходимость в обратном проходе через
   Whisper, что сокращает время одной итерации обучения в несколько раз.

## 3.5. Видео-энкодер

Видео-энкодер построен по классической для AVSR схеме «3D-Conv →
ResNet-18 → Transformer» (см. раздел 2.2.3) и состоит из трёх частей.

### 3.5.1. Visual Frontend (3D-Conv + ResNet-18)

**Conv3D-блок** служит для извлечения признаков движения губ:

- ядро размером `(5, 7, 7)` по осям `(время, высота, ширина)`;
- stride `(1, 2, 2)` — пространственное уменьшение в 2 раза, временное
  разрешение сохраняется;
- 64 выходных канала;
- BatchNorm3d, ReLU, MaxPool3d.

Выходная размерность: `(B, 64, T_v, 24, 24)`. Окно из 5 кадров при
25 FPS соответствует 200 мс — длительности одной виземы.

**ResNet-18 backbone** обрабатывает каждый кадр независимо как 2D-карту:

- адаптированный первый слой (Conv2d 64→64 вместо стандартного 3→64);
- стандартные блоки layer1, layer2, layer3, layer4 ResNet-18 со
  смещёнными размерностями 64 → 64 → 128 → 256 → 512;
- AdaptiveAvgPool2d(1) для получения одного вектора на кадр.

На выходе frontend: тензор `(B, T_v, 512)` — один 512-мерный вектор на
кадр. ResNet-18 обучается с нуля (без инициализации весами ImageNet,
по причинам, описанным в разделе 2.2.3).

### 3.5.2. Temporal Encoder (Transformer)

Поверх кадровых эмбеддингов установлен Transformer-энкодер для
моделирования долгих временных зависимостей:

- линейная проекция 512 → `d_model = 512`;
- синусоидальное позиционное кодирование (Vaswani et al., 2017);
- стек из 4 слоёв `TransformerEncoderLayer` с 8 головами внимания,
  размерностью feed-forward 4·d_model = 2048, dropout = 0.1;
- pre-norm архитектура (`norm_first=True`) для большей стабильности
  обучения;
- маска паддинга формируется на основе реальных длин видео
  (`video_lens`), что предотвращает утечку информации из западдленных
  позиций.

На выходе: `(B, T_v, 512)`.

## 3.6. Модуль слияния модальностей

В работе реализованы два альтернативных модуля слияния: простая
конкатенация (ConcatFusion) и слияние через перекрёстное внимание
(CrossAttentionFusion). Оба модуля имеют одинаковый интерфейс и
взаимозаменяемы; выбор контролируется параметром `cfg.model.fusion.type`.

### 3.6.1. ConcatFusion (базовый вариант)

Простейший вариант слияния, используемый в качестве базовой линии для
сравнения:

1. Видео-фичи `(B, T_v, 512)` линейно интерполируются по временной оси
   до длины аудио-фичей `T_a`. Получаем `(B, T_a, 512)`.
2. Конкатенация по фичевой оси: `(B, T_a, d_audio + d_video)`.
3. Линейная проекция `Linear(d_audio + d_video, d_model)` с
   последующими `LayerNorm` и `ReLU`.

На выходе: `(B, T_a, d_model)`. Длительность выхода наследуется от
аудио, что соответствует выбору аудио-временной оси как «опорной».

Принципиальное ограничение конкатенации — отсутствие **динамического
перевзвешивания** модальностей. Линейный слой смешивает их с
усреднёнными по обучающей выборке весами и не способен в инференсе
адаптироваться к ситуации, когда одна из модальностей зашумлена.

### 3.6.2. CrossAttentionFusion (основной вариант)

Основной вариант слияния основан на механизме перекрёстного внимания.
Архитектура состоит из 2 идентичных блоков, в каждом из которых
происходит обмен информацией между модальностями в обоих направлениях.

Один блок:

```
audio'  = audio  + MHA(Q = audio,  K = video, V = video,  mask = video_mask)
audio'' = audio' + FFN(LayerNorm(audio'))

video'  = video  + MHA(Q = video,  K = audio, V = audio,  mask = audio_mask)
video'' = video' + FFN(LayerNorm(video'))
```

где MHA — `nn.MultiheadAttention` (8 голов, batch_first), FFN —
двухслойная сеть с GELU и dropout = 0.1, LayerNorm применяется в
pre-norm стиле.

В первом блоке `audio → video`: каждый аудио-токен «опрашивает» все
видео-токены, забирая взвешенную сумму. Содержательно: для каждого
момента звука модель решает, **какие кадры видео сейчас релевантны**.
Это реализует мягкое выравнивание (soft alignment) между модальностями,
важное в силу того, что видимое движение губ часто опережает звук на
1–2 кадра.

Симметричный механизм `video → audio` дополнительно обогащает видео
аудио-контекстом.

После 2 блоков выполняется финальное слияние: видео интерполируется до
длины аудио, конкатенируется по фичевой оси, проецируется обратно в
`d_model` с `LayerNorm`. На выходе: `(B, T_a, d_model)`.

## 3.7. Выходная CTC-голова

Слитые признаки `(B, T, d_model)` подаются на линейный слой
`Linear(d_model, vocab_size)`, где `vocab_size = 29` — размер
символьного алфавита системы.

### 3.7.1. Алфавит

Символьный алфавит включает следующие токены:

| Индекс | Токен | Описание |
|--------|-------|----------|
| 0 | `<blank>` | специальный токен для CTC |
| 1–26 | a–z | строчные буквы латинского алфавита |
| 27 | ` ` | пробел |
| 28 | `'` | апостроф (для слов вроде `don't`, `it's`) |

Перед токенизацией текст проходит **нормализацию**: приведение к нижнему
регистру, унификация различных видов апострофов и кавычек до одного
ASCII-символа `'`, замена цифр и пунктуации на пробелы, схлопывание
последовательностей пробелов.

### 3.7.2. Функция потерь CTC

В качестве функции потерь используется `torch.nn.CTCLoss`. CTC требует
формат логитов `(T, B, V)` с применённым `log_softmax` по оси V, а
также передачу длин выходов модели (`out_lens`) и длин целевых
последовательностей (`text_lens`). Целевые последовательности
передаются в виде одного плоского тензора (конкатенация всех текстов
батча), что предусмотрено в `avsr_collate_fn`.

Параметр `zero_infinity = True` устанавливает бесконечно большие
значения функции потерь в ноль, что предотвращает срыв обучения на
коротких примерах, для которых число выходных фреймов модели может
оказаться меньше длины целевого текста.

### 3.7.3. Декодирование

В работе используется **жадное CTC-декодирование** (greedy decoding):

1. Argmax по последней оси даёт последовательность индексов токенов.
2. Подряд идущие одинаковые токены схлопываются в один.
3. Из получившейся последовательности удаляются все `<blank>` токены.
4. Оставшиеся индексы декодируются в строку через обратный словарь
   токенизатора.

Жадное декодирование выбрано как наиболее быстрое и не требующее
языковой модели. Более качественные методы (beam search с интеграцией
LM) можно подключить в дальнейшем без изменения архитектуры модели.

## 3.8. Стратегия обучения

### 3.8.1. Modality dropout

Для обеспечения устойчивости модели к ситуации отсутствия одной из
модальностей в инференсе применяется **modality dropout**: с
вероятностью `p_drop = 0.1` обнуляется аудио-ветка, и с такой же
вероятностью — видео-ветка. С вероятностью `1 - 2·p_drop = 0.8`
модель видит обе модальности.

Такая схема позволяет одной и той же модели работать в трёх режимах:
audio+video (основной), audio-only (при потере детекции лица),
video-only (при отказе микрофона или сильном шуме, который воспринимается
моделью как «тишина»). Modality dropout активен только в режиме обучения
(`self.training == True`); в инференсе модель использует обе модальности
без обнуления.

### 3.8.2. Аугментация данных

В работе применяются следующие аугментации:

**SpecAugment** (Park et al., 2019) — маскирование случайных полос частот
и времени в мел-спектрограмме. Параметры: 1 частотная маска шириной до
27 полос, 2 временных маски шириной до 10 фреймов каждая. Применяется
только в обучении.

**Шумовая аугментация**. Для целей экспериментов на устойчивость к шуму
в `scripts/eval.py` реализовано наложение белого гауссова шума на
мел-спектрограммы с заданным SNR (от 0 до 20 дБ). Шум добавляется в
пространстве спектрограмм, что является упрощённой моделью реального
акустического шума, но достаточной для демонстрации эффекта
мультимодальности.

### 3.8.3. Оптимизатор и расписание скорости обучения

- Оптимизатор: AdamW с `lr = 1e-4` и `weight_decay = 0.01`.
- Расписание скорости обучения: **линейный warmup** в течение первых
  1000 шагов (от 0 до lr), затем **косинусный спад** до нуля к концу
  обучения.
- Gradient clipping: норма градиентов ограничена 5.0 во избежание
  «взрывов».

### 3.8.4. Смешанная точность и накопление градиентов

Для ускорения обучения и снижения потребления памяти GPU используется
**смешанная точность** (FP16) через `torch.cuda.amp.autocast` и
`GradScaler`. Это ускоряет обучение примерно в 1.5–2 раза на GPU с
поддержкой Tensor Cores.

Для имитации большего эффективного размера батча используется
**накопление градиентов** (gradient accumulation): фактический батч
размером 4 умножается на коэффициент 4, что даёт эффективный размер
батча 16 без увеличения потребления памяти на одном шаге.

### 3.8.5. Сохранение и возобновление

В силу того, что бесплатные GPU-среды (Colab, Kaggle) ограничивают
непрерывное время работы (обычно 6–12 часов), реализован полный
**checkpoint/resume** механизм. После каждой эпохи сохраняются:

- веса модели;
- состояние оптимизатора;
- состояние планировщика скорости обучения;
- состояние GradScaler;
- номер последней эпохи;
- лучшее значение WER на валидации.

При запуске обучения с флагом `--resume <путь_к_чекпоинту>` все эти
состояния восстанавливаются и обучение продолжается с прерванной
эпохи.

## 3.9. Пайплайн инференса в близком к реальному времени режиме

Для демонстрации работы системы в режиме, близком к реальному времени,
реализован модуль `OfflineDemo` в файле `src/inference/realtime.py`.
Модуль принимает на вход видеофайл, последовательно прогоняет его через
пайплайн предобработки и инференса модели и возвращает транскрипцию
вместе с замеренными метриками задержки и Real-Time Factor (RTF):

```
RTF = время_инференса / длительность_аудио
```

RTF < 1.0 означает, что система обрабатывает аудио быстрее, чем оно
звучит, и пригодна для реального времени. Целевое значение задержки —
менее 500 мс.

Демонстрационный интерфейс реализован с использованием библиотеки
**Gradio**, которая позволяет запустить веб-интерфейс одной командой:
пользователь загружает видеофайл через браузер и получает
транскрипцию вместе с метриками. Такой интерфейс используется при
защите курсовой работы.

Полноценный потоковый режим с захватом с веб-камеры и микрофона
заложен в архитектуру (раздел 5.2 исходного плана), но в рамках
настоящей курсовой выходит за рамки приоритетных задач.

## 3.10. Резюме главы

В настоящей главе подробно описана архитектура разработанной AVSR-системы
и методика её обучения. Ключевые проектные решения:

1. Замороженная аудио-ветка на основе предобученной модели Whisper-small.
2. Обучаемая с нуля видео-ветка, состоящая из 3D-свёрточного фронтенда,
   ResNet-18 backbone и 4-слойного Transformer-энкодера.
3. Модуль слияния модальностей через 2 блока двунаправленного
   перекрёстного внимания (плюс альтернативный модуль простой
   конкатенации для аблации).
4. CTC-голова с символьным алфавитом из 29 токенов для обеспечения
   потокового декодирования.
5. Стратегия обучения, включающая modality dropout, SpecAugment,
   смешанную точность (FP16), накопление градиентов, линейный warmup
   с косинусным спадом и полный механизм сохранения/возобновления.
6. Демонстрационный интерфейс на Gradio для оценки задержки и
   качества работы в режиме, близком к реальному времени.

Результаты экспериментальной оценки данной системы представлены в
следующей главе.
